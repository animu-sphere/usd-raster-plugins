# OST workspace cells in a bundle-free repository

- Date: 2026-08-23
- Consumer release target: `v0.1.0` (milestones 0 and 1)
- Repository revision: `0f9b795` (`feat/repository-skeleton-and-raster-core`)
- OST version exercised locally: `ost 0.22.2`
- Runtime: `cy2026` / OpenUSD 26.08
- Platform: Windows x86_64
- Target: `cy2026-windows-x86_64-py313-usd`
- Scope: stand up the first CI matrix for a repository whose libraries land
  before its first plugin bundle
- Upstream ask: one P2, carried below

This is an engineering dogfooding record for the repository skeleton. The
inspected revision implements milestones 0 and 1: two plain static libraries,
`usdGeoCore` and `usdRasterCore`, with no plugin bundle, no tool, and no format
reader. `plugins/raster-geotiff` arrives at milestone 2.

That shape — libraries first, bundle later — is what this report is about. It
is the ordinary consequence of the workspace contract's rule that a directory
is created when its first tested capability is implemented, and it is the shape
`ost 0.22.2` currently has no green CI path for.

## TL;DR

`kind: workspace` cells are the right declaration for a library-only
repository, and `ost build` and `ost test` both succeed against the pinned
runtime. But every generated workspace job opens with a dependency-graph rung
that fails closed when the workspace contains no bundle, so the generated
workflow cannot go green until a bundle exists. The repository therefore
declares the matrix but does not commit the generated workflow yet.

No repository-side configuration avoids this. The guard is upstream of the
cell declaration.

## 3. What worked

`kind: workspace` is exactly the cell shape this repository needed, and it was
easy to find. The doc comment on `CellKind::Workspace` describes the problem it
solves in the same terms this repository has it:

> A workspace member that no bundle requires — a plain library, or a CLI
> executable built from the workspace against the runtime — was therefore
> invisible to CI, with no cell shape able to name it.

`ost build` resolved the pinned `cy2026` / `usd` environment and drove the root
CMake tree, including the `USDRASTER_BUILD_TESTS` targets, with no
repository-side coaxing. `ost test` ran the CTest suite and reported 4 of 4
passing, including the two Python repository-level checks the root
`CMakeLists.txt` registers alongside the two C++ suites. Neither verb needed a
bundle.

`ost ci validate` rejecting an empty `cells:` list was also correct and useful.
The first attempt at this matrix declared `cells: []` with the bundle cells
commented out for milestone 2, and the resulting

```text
error[MANIFEST_INVALID]: manifest is invalid: the support matrix declares no cells
```

is what prompted looking for a cell shape that could name the libraries,
rather than shipping a matrix that asserted nothing. That is the diagnostic
doing its job.

## 4. The blocker

Both generated workspace job shapes emit the dependency-graph rung
unconditionally. From `crates/ost-ci/src/github.rs`:

```rust
fn workspace_steps(matrix: &SupportMatrix) -> String {
    format!(
        "\
{preamble}\
      - name: Validate the workspace dependency graph
        shell: bash
        run: ost plugin test --workspace --graph-only --json
      - name: Build the workspace from source
        ...
```

The function's own doc comment states the intent:

> The graph rung has a job of its own ([`workspace_graph_steps`]), so every
> step here builds: only the CTest rung is gated.

So a `verify: test` cell runs graph, then build, then test; a `verify: build`
cell runs graph, then build; and a `verify: graph` cell runs graph alone. Every
rung of the ladder starts with the step that fails here.

The failure comes from `load_workspace_graph` in
`crates/ost-cli/src/commands/plugin.rs`:

```rust
fn load_workspace_graph() -> Result<(Vec<Bundle>, Vec<Library>, ost_plugin::WorkspaceValidation)> {
    let members = discover_workspace_members(Utf8Path::new("."))?;
    if members.bundles.is_empty() {
        return Err(
            Error::precondition("no plugin bundles found in the workspace member set").with_hint(
                "run from the workspace root, or pass a bundle path instead of --workspace",
            ),
        );
    }
    ...
```

Observed, from the workspace root:

```text
$ ost plugin test --workspace --graph-only --json
{
  "error": {
    "category": "precondition",
    "code": "PRECONDITION_FAILED",
    "hint": "run from the workspace root, or pass a bundle path instead of --workspace",
    "message": "no plugin bundles found in the workspace member set"
  },
  "ok": false,
  "schema": 1,
  "warnings": []
}
$ echo $?
4
```

Both branches of the hint are unavailable here. The command *was* run from the
workspace root, and there is no bundle path to pass instead.

The same guard is duplicated in `package_workspace`, and `load_workspace_graph`
is shared by `validate_workspace_graph`, `test_workspace`, and
`test_workspace_from_package` — so every `--workspace` entry point except
`ost build` and `ost test` is closed to a bundle-free repository.

## 5. Why this reads as a gap rather than as correct fail-closed behavior

`ost ci validate` rejecting an empty matrix is right: a matrix that asserts
nothing is a matrix that cannot fail. The graph guard is a different case,
because the work behind it is still meaningful with zero bundles.

`load_workspace_graph` discovers bundles, libraries, and tools, and the guard
sits *upstream* of all three loads. Past the guard it would:

- load every `openstrata.library.yaml` through `Library::load`, catching a
  malformed or unreadable descriptor;
- load every tool descriptor, which the function's own comment says is done
  "so an unreadable or invalid descriptor cannot disappear from the gate";
- call `validate_workspace_with_libraries(&bundles, &libraries)`, which on an
  empty bundle list has no edges to check and is trivially valid.

Two of those three still have something to say about this repository. It
declares two library descriptors, and a typo in either — a wrong `cmake.target`,
a duplicated `library.id` — is exactly what a graph gate should catch, and is
currently invisible to it. The rung would not be vacuous; it would be a
descriptor-validity gate with an empty edge set.

That the same run is being asked to prove nothing about bundle edges is not a
reason to refuse it. It is the accurate result for a workspace that has no
bundles yet.

## 6. What this repository did instead

The matrix declares six `kind: workspace` cells — pull-request and mainline
lanes on Windows, macOS arm64, and Linux — and `ost ci validate` accepts them.
The bundle cells for `plugins/raster-geotiff` are written out in the same file,
commented, with the pinned digests already in place, and are uncommented in the
pull request that creates the bundle.

The generated `.github/workflows/ost-source-ci.yml` is **not committed**.
Committing a workflow whose first step is known to fail would put six red
checks on every pull request and train reviewers to ignore CI. It is generated
in the same pull request that creates the bundle.

Until then the gate is a hand-written `.github/workflows/core-ci.yml`: plain
CMake with `-DUSDRASTER_CORE_ONLY=ON`, on all three hosts, with no runtime SDK
materialized at all. That lane is required by the workspace contract
independently of this blocker — it is what proves the core libraries have not
acquired an OpenUSD dependency — and `ost ci generate` correctly cannot express
it, since no cell shape can say "and nothing is available".

The coverage cost today is zero. Every target currently in the tree is
OpenUSD-free, so the core lane builds and tests all of them; there is nothing
the runtime lane would reach that the core lane does not. The cost is that the
runtime lane's *own* correctness — the pinned digests, the host packages, the
`host_python` provisioning — goes unexercised in CI until milestone 2, and will
land in one step rather than incrementally.

## Ask summary

| Priority | Ask for OpenStrata | Why it matters | Workaround used here |
| --- | --- | --- | --- |
| P2 | Let `ost plugin test --workspace --graph-only` succeed on a workspace with zero bundles, validating the library and tool descriptors and reporting an empty edge set | A repository whose libraries land before its first bundle is a normal shape under a "create a directory when its first capability lands" rule, and `kind: workspace` cells exist precisely to give those libraries CI. Today the cell shape is declarable but not runnable, so such a repository has no runtime-backed CI at all | Declare the matrix, do not commit the generated workflow, and gate on a hand-written plain-CMake lane until a bundle exists |

A compatible shape would move the emptiness check from a hard precondition to
a reported condition: keep the current error when a bundle path was explicitly
requested and is missing, and let `--workspace` proceed through the descriptor
loads with zero bundles, emitting a warning in the `warnings` array the JSON
envelope already carries. Repositories that expect bundles would still see the
warning surface in CI logs; repositories that do not have one yet would get a
green, meaningful gate.

If preserving fail-closed behavior by default matters more, an explicit opt-in
on the cell — something like `allow_bundleless: true` — would also unblock
this, at the cost of a knob that only exists for early-milestone repositories.
The warning form seems preferable because it needs no new matrix surface and
degrades correctly for both kinds of repository.

Either way, the guard's current hint should stop suggesting the two remedies
that a bundle-free workspace root cannot take.
